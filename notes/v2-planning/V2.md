## 1. What V2 Is

V2 is not a rewrite. It is a set of architectural decisions that, when applied incrementally, move the codebase from its current state (correct stack, drifted structure) to a state where the structure is as correct as the stack.

**The four core bets:**

1. **Domain-first organization** — folders map to the product's conceptual domains, not to page names or Polymarket API endpoints
2. **Server as truth for session** — auth state lives in a server query, not localStorage; this eliminates an entire class of stale-state bugs
3. **WebSocket as cache updater** — real-time data flows into TanStack Query's cache; Zustand never mirrors server state
4. **One error type** — `AppError extends TRPCError`; no duck-typing, no two competing patterns

---

## 2. Principles

These are the load-bearing rules. Every architectural decision below follows from them.

**P1: Source of truth is singular.**
Every piece of state has exactly one owner. Server data lives in TanStack Query. User input lives in Zustand. Real-time events write into TanStack Query's cache. No state exists in two places simultaneously.

**P2: Names speak the domain, not the infrastructure.**
A router called `clob` requires knowing what CLOB means. A router called `orders` does not. A folder called `features/explore` describes a page. A folder called `domains/explore` describes the same concept without the `features/` indirection. Infrastructure names (`clob`, `data`, `wallets`) are always wrong. Domain names (`orders`, `portfolio`, `tracker`) are always right.

**P3: The server knows who you are.**
Auth state is not stored in localStorage. The server's JWT cookie is the ground truth. The client asks the server who it is on load; it does not reconstruct identity from cached localStorage values. This eliminates the stale-session class of bugs permanently.

**P4: Components do one thing.**
A component either fetches data or renders it — not both in a large blob. Route modules prefetch. Domain containers orchestrate state and queries. Design system components receive props and render HTML. These tiers never mix.

**P5: The WebSocket is plumbing, not state.**
A WebSocket message is an event that updates a cache. It is not a data source that a component subscribes to directly. Components read from TanStack Query. The WebSocket updates TanStack Query. Components never know about the WebSocket.

**P6: Explicit over magic.**
No barrel files in app code. No `index.ts` re-exports in feature folders. Import from the actual file. Mistakes are compile errors, not runtime surprises.

### The "what tech for real-time" decision specifically

The Polymarket ecosystem has four distinct real-time feeds:
- **Market channel** — orderbook snapshots + deltas, price changes (CLOB WebSocket, public)
- **User channel** — order fills, order status changes (CLOB WebSocket, authenticated)
- **RTDS** — crypto prices, equity prices, and comments (RTDS WebSocket, public)
- **Sports** — live game scores (Sports WebSocket, public)

All four are handled by the **WebSocket hub** (see §10). Components never subscribe directly to any of these. They read from TanStack Query. The hub is what keeps TanStack Query current.

## 4. Package Map

Packages contain code that is used by more than one app, or code whose boundary is meaningful for testing in isolation. They do not exist for organizational purposes alone.

```
packages/
  api/              # tRPC server infrastructure — apps/server only (keeping current name)
  contract/         # AppRouter type re-export + RouterOutput/RouterInput helpers — apps/web + apps/server
  db/               # Drizzle schema, client, query helpers — apps/server only
  types/            # Shared domain types, branded primitives, constants — everywhere
  env/              # T3 Env schemas — everywhere
  hooks/            # Shared React utility hooks — apps/web only
  logger/           # Pino logger (client + server variants) — everywhere
  config/           # TypeScript + Biome configuration presets — everywhere
```

### packages/api (keeping current name)

**What:** tRPC server infrastructure. `initTRPC`, `publicProcedure`, `protectedProcedure`, `AppError`, auth middleware, session utilities, CLOB client factory, crypto helpers.

**Why not renamed:** The name `@doji/api` accurately describes what it is — the API contract between server and client. The router keys (`clob` → `orders`, `data` → `portfolio`/`activity`/`leaderboard`) are what get renamed, not the package itself.

**Consumed by:** `apps/server` only.

```
packages/api/src/
  index.ts            # exports: t, publicProcedure, protectedProcedure, AppError, Context
  trpc.ts             # initTRPC.context<Context>() with error formatter
  context.ts          # Context type, createContextInner
  errors.ts           # AppError extends TRPCError — the one error class
  session.ts          # createSessionToken, verifySessionToken
  middleware/
    auth.ts           # extracts Bearer token, verifies session, populates ctx.session
    logger.ts         # request-scoped Pino logger
    sentry.ts         # Sentry breadcrumbs per request
  clob/
    client.ts         # ClobClient constructor + auth injection
    factory.ts        # getClobClient(ctx) — creates authenticated client
    address-signer.ts # AddressSigner for CLOB auth
  crypto.ts           # AES-256-GCM encrypt/decrypt
```

### packages/contract (renamed from packages/api's client-facing role)

**What:** The API contract. Re-exports `AppRouter` type from `apps/server`. Pre-computes `RouterOutput` and `RouterInput` inference helpers. Zero runtime code — type imports only.

**Why:** Eliminates 8+ direct `import type { AppRouter } from "server/routers/index"` in the web app. The web app should not reach into server internals.

```
packages/contract/src/
  index.ts    # export type { AppRouter } from "server/routers/index"
              # export type { RouterOutput, RouterInput }
              # export type helpers: InferProcedureOutput<T>, InferProcedureInput<T>
```

### tRPC Transformer (deferred)

superjson is not currently used and not needed — Polymarket API returns ISO strings for dates, not Date objects. If we later need to pass Date/Map/Set/BigInt across the tRPC boundary, add superjson then. For now, no transformer.

### createCallerFactory for RSC

For calling tRPC procedures inside React Server Components, use `createCallerFactory` combined with React's `cache()` to ensure one context is created per request (not per call):

```ts
// lib/trpc/server.ts
import "server-only";
import { cache } from "react";
import { headers } from "next/headers";
import { createCallerFactory } from "@doji/server";
import { appRouter } from "server/routers";
import { createContext } from "server/context";

const createCaller = createCallerFactory(appRouter);

// React.cache() dedups across the same RSC render tree
export const trpc = cache(async () => {
  const ctx = await createContext({ req: { headers: await headers() } });
  return createCaller(ctx);
});
```

Usage in route modules:
```ts
// app/(app)/market/[slug]/page.tsx
const caller = await trpc();
const market = await caller.markets.getBySlug({ slug });
```

This is the correct pattern — not the legacy `createServerSideHelpers` approach.

### packages/db

Drizzle schema, client, and query helpers. Unchanged from current, with additions noted in §14.

### packages/types

Shared domain types. The rule: **types that are consumed by both the server and web app live here**. Types that are only used server-side live in the server package. Types that are only used client-side live in the domain that uses them.

Branded primitives are enforced more strictly in V2:
```ts
// packages/types/src/branded.ts
declare const __brand: unique symbol;
type Brand<T, B> = T & { [__brand]: B };

export type TokenId     = Brand<string, "TokenId">;
export type ConditionId = Brand<string, "ConditionId">;
export type MarketSlug  = Brand<string, "MarketSlug">;
export type EventSlug   = Brand<string, "EventSlug">;
export type OrderId     = Brand<string, "OrderId">;
export type UserId      = Brand<string, "UserId">;
export type Address     = Brand<string, "Address">;

// Runtime constructors — the only way to create branded values
export const tokenId     = (s: string): TokenId     => s as TokenId;
export const conditionId = (s: string): ConditionId => s as ConditionId;
export const marketSlug  = (s: string): MarketSlug  => s as MarketSlug;
// etc.
```

Passing a raw `string` to a function expecting `TokenId` is now a compile error. This is the point.

## 5. Domain Model

The domain entities and their relationships. This drives everything downstream.

```
Event ──has many──► Market ──has──► Orderbook (live)
                      │                ├── Bid levels [ { price, size, cumulative } ]
                      │                └── Ask levels [ { price, size, cumulative } ]
                      │
                 Yes Token ──► Position (user holds N shares)
                 No Token  ──► Position (user holds N shares)
                      │
                    Order ──► Fill/Trade (immutable once settled)
                    (GTC / GTD / FOK / FAK)

User
  └── Session    (JWT, expires, stored in HttpOnly cookie)
  └── Wallet     (EOA address, chainId, signatureType)
  └── Safe       (Gnosis Safe, funder address for CLOB trading)
  └── Balance    (pUSD on Safe, CTF token balances)
  └── Watchlist  (saved markets)
  └── Tracked Wallets (other traders being monitored)
```

**Source of truth per entity:**

| Entity | Source | Volatility | Owned by |
|--------|--------|-----------|---------|
| Event | Gamma API | Low (hours) | TanStack Query |
| Market | Gamma API | Low (minutes) | TanStack Query |
| Orderbook | CLOB WS → REST snapshot | High (ms) | TanStack Query (WS-updated) |
| Order | CLOB API + WS | Medium | TanStack Query (WS-updated) |
| Position | Data API + WS events | Medium | TanStack Query (WS-invalidated) |
| Fill/Trade | Data API | Immutable | TanStack Query |
| Balance | On-chain + Data API | Medium | TanStack Query |
| Session | Server JWT | Expires | TanStack Query (`trpc.auth.me`) |
| Wallet connection | Browser wallet | User-driven | Zustand (persisted) |
| Order form | User input | User-driven | Zustand (persisted) |
| Layout prefs | User input | User-driven | Zustand (persisted) |
| Optimistic deltas | In-flight trade | Ephemeral | Zustand (NOT persisted) |

### Router philosophy

Routers are thin. They:
1. Define the procedure (public or protected)
2. Parse input with Zod
3. Call a service or query helper
4. Return the result

They do not contain business logic. They do not contain API client code. A router file should rarely exceed 200 lines. If it does, extract a service.

```ts
// ✅ Correct: thin router delegating to a service
export const ordersRouter = router({
  place: protectedProcedure
    .input(placeOrderSchema)
    .mutation(async ({ ctx, input }) => {
      return placeOrder(ctx, input); // all logic in services/clob-write.ts
    }),
});

// ❌ Wrong: router containing inline API client calls and business logic
export const ordersRouter = router({
  place: protectedProcedure
    .input(placeOrderSchema)
    .mutation(async ({ ctx, input }) => {
      const client = new ClobClient(...);
      const result = await client.postOrder(...);
      // 50 more lines of transformation and error handling
    }),
});
```

## 7. Router Contract

The full tRPC router surface in V2. This is the API contract between server and client.

```ts
export const appRouter = router({

  // ─── Identity & Onboarding ───────────────────────────────────────────────
  auth: router({
    // Session
    login:               publicProcedure    // Magic DID token → session cookie
    walletLogin:         publicProcedure    // SIWE signature → session cookie
    walletChallenge:     publicProcedure    // get signable SIWE challenge message
    logout:              protectedProcedure // revoke JWT jti, clear cookie
    me:                  protectedProcedure // current session — the useSession() source
    // Onboarding
    registerSafe:        protectedProcedure // verify onchain + persist Safe address
    approvalStatus:      protectedProcedure // check pUSD/CTF allowances for Safe
  }),

  // ─── Market Discovery ────────────────────────────────────────────────────
  // Gamma API proxy. All public — no auth needed to browse.
  events: router({
    list:                publicProcedure    // cursor-paginated event list (keyset: after_cursor)
    getBySlug:           publicProcedure    // event + child markets by slug
    search:              publicProcedure    // text search across events, markets, profiles
    sports:              publicProcedure    // sports-category events
    teams:               publicProcedure    // team metadata for a game event
    tags:                publicProcedure    // tag list + tag→tag relationships
    seriesList:          publicProcedure    // recurring market series (e.g. "Weekly BTC price")
    seriesById:          publicProcedure    // single series with its constituent events
    comments:            publicProcedure    // threaded comments for a market entity
    publicProfile:       publicProcedure    // public trader profile by wallet address
    resolveTrader:       publicProcedure    // resolve a trader identity for the trades tab
  }),

  markets: router({
    list:                publicProcedure    // cursor-paginated market list (keyset: after_cursor)
    getBySlug:           publicProcedure    // market detail by Gamma slug
    getById:             publicProcedure    // market detail by condition ID
    getByToken:          publicProcedure    // parent market for a given token ID
    related:             publicProcedure    // related markets (shown in order form panel)
    calendarList:        publicProcedure    // markets for the calendar widget
    listByGameId:        publicProcedure    // all markets in a sports game
    // CLOB read-only market data (moved from clob.* router)
    orderbook:           publicProcedure    // single-token orderbook snapshot
    orderbooks:          publicProcedure    // batch orderbook for multiple tokens (max ~20)
    priceHistory:        publicProcedure    // OHLC price history for one token
    priceHistoryBatch:   publicProcedure    // price history for multiple tokens in one call
    tickSize:            publicProcedure    // minimum price increment for a token
    midpoint:            publicProcedure    // (bestBid + bestAsk) / 2
    spread:              publicProcedure    // bestAsk − bestBid
    lastPrices:          publicProcedure    // last trade prices for up to 500 tokens
    marketPrice:         publicProcedure    // best bid (BUY) or best ask (SELL) for a token+side
    feeRate:             publicProcedure    // base maker/taker fee rate for a token
    clobInfo:            publicProcedure    // all CLOB params in one call: tokens, tick, fees, rewards, RFQ status
    holders:             publicProcedure    // top position holders for a market
    serverTime:          publicProcedure    // CLOB server Unix timestamp (for client clock sync)
  }),

  // ─── Trading ─────────────────────────────────────────────────────────────
  // All protected — require authenticated session.
  orders: router({
    // Queries
    open:                protectedProcedure // open orders enriched with market data
    getById:             protectedProcedure // single order by ID (order hash)
    trades:              protectedProcedure // filled trades for the authenticated user
    builderTrades:       protectedProcedure // trades attributed to our builder code
    scoringStatus:       protectedProcedure // is a given order scoring for LP rewards?
    scoringStatusBatch:  protectedProcedure // batch: map of order IDs → scoring boolean (GET or POST)
    closedOnlyMode:      protectedProcedure // is the user in closed-only mode? (can only close positions)
    balanceAllowance:    protectedProcedure // current pUSD/CTF balance + spender allowances on the Safe
    // Mutations
    place:               protectedProcedure // post one signed order (max 1) — ⚠️ no true market orders;
                                            //   simulate with aggressive pricing (BUY: min(0.99, ask*1.05),
                                            //   SELL: max(0.01, bid*0.95)) + FOK type
                                            //   Response statuses: live (on book), matched (filled immediately),
```

### Naming rules applied
- **Queries:** noun or noun phrase. No `get` prefix — it's redundant on a query.
  - `orders.open` not `orders.getOpenOrders`
  - `markets.orderbook` not `markets.getOrderBook`
  - `portfolio.positions` not `portfolio.getPositions`
- **Mutations:** verb.
  - `orders.place` not `orders.createAndPostOrder`
  - `orders.cancel` not `orders.cancelOrder`
  - `watchlist.toggle` not `watchlist.toggleWatchlistItem`
- **No infrastructure names:** `clob` → `orders`, `data` → `portfolio`/`activity`, `wallets` → `tracker`

### Pagination contract

All list endpoints that can return large result sets use **cursor-based (keyset) pagination**. The `offset` parameter is explicitly rejected by the Polymarket API — use `after_cursor` instead.

```ts
// Standard pattern for all paginated list queries
const { data, fetchNextPage, hasNextPage } = useInfiniteQuery(
  trpc.events.list.infiniteQueryOptions(
    { limit: 20, ...filters },
    { getNextPageParam: (last) => last.next_cursor ?? undefined }
  )
);
```

This applies to: `events.list`, `markets.list`, `orders.open`, `orders.trades`, `activity.feed`, `leaderboard.rankings`.

**`maxPages` for memory-bounded infinite scroll (TanStack Query v5):** Long browsing sessions on explore/leaderboard accumulate pages in memory. Use `maxPages` to cap stored pages and `getPreviousPageParam` for bi-directional scrolling:

```ts
const { data, fetchNextPage, fetchPreviousPage, hasNextPage } = useInfiniteQuery(
  trpc.events.list.infiniteQueryOptions(
    { limit: 20, ...filters },
    {
      getNextPageParam: (last) => last.next_cursor ?? undefined,
      getPreviousPageParam: (first) => first.prev_cursor ?? undefined,
      maxPages: 5, // Only keep 5 pages in memory — older pages evicted
    }
  )
);
```

### Heartbeat contract

`orders.heartbeat` **must** be called on a regular interval by any client with open orders. If the heartbeat lapses, the CLOB automatically cancels all open orders for that user. This is a safety mechanism for automated trading — it ensures orders are cleaned up if the client becomes unresponsive.

Consequence for V2: `use-clob-heartbeat.ts` stays. It is mounted for the duration of any trading session where the user has open orders. It should stop firing after `orders.cancelAll` or on logout.

### Matching engine maintenance

The CLOB matching engine can enter a **maintenance window** during which new order placement is unavailable. The `markets.clobInfo` procedure returns `{ matchingEngineActive: boolean }`. When `matchingEngineActive` is `false`, the order form should disable submission and show a maintenance notice. Open orders and cancellations still work during maintenance. The trading guard should check `clobInfo` alongside `market.acceptingOrders` before enabling the submit button.

### `clobInfo` response shape (from CLOB `/clob-markets/{condition_id}`)

The `markets.clobInfo` procedure wraps the CLOB's `ClobMarketDetails` schema. The response uses abbreviated field names:

```ts
type ClobMarketDetails = {
  t: Array<{ t: string; o: string }>;  // tokens: [{ t: tokenId, o: "Yes"|"No" }]
  mts: number;   // minimum tick size (e.g. 0.01)
  mos: number;   // minimum order size (e.g. 5)
  mbf: number;   // maker base fee (bps)
  tbf: number;   // taker base fee (bps)
  rfqe: boolean; // RFQ (Request for Quote) enabled
  itode: boolean;// taker order delay enabled
  ibce: boolean; // Blockaid check enabled
  oas: number;   // minimum order age (seconds) before scoring
  gst: string | null; // game start time (ISO 8601, sports markets only)
  fd: {          // fee details (fee curve parameters)
    r: number | null;   // fee rate
    e: number | null;   // fee curve exponent
    to: boolean | null; // taker-only fees
  } | null;
  r: object;     // rewards configuration (dynamic shape)
};
```

### Order response statuses

`orders.place` returns a `SendOrderResponse` with one of three statuses:
- **`live`** — order placed on the book, waiting for a match
- **`matched`** — order immediately filled (includes `transactionsHashes` and `tradeIDs`)
- **`delayed`** — order deferred (when `deferExec: true` or system-initiated delay)

The order form should handle all three: `live` → show in open orders, `matched` → trigger post-trade invalidation, `delayed` → show pending state with polling.

### Trade schema fields

The CLOB trade response includes fields not surfaced in V1:
- `fee_rate_bps` — fee rate in basis points for this trade
- `trader_side` — `"TAKER"` or `"MAKER"` (which side of the trade the user was on)
- `maker_orders[]` — array of maker orders matched against (order_id, matched_amount, price, fee_rate_bps)
- `match_time_nano` — nanosecond-precision match timestamp (for ordering trades within the same second)

These should be included in the trade display (trades tab, activity feed) and are useful for fee analytics.

### Notifications (CLOB API — future consideration)

The CLOB API exposes a notifications system (`GET /notifications`, `DELETE /notifications`) with 6 event types:
1. Order cancellation
2. Order fill (taker or maker)
3. Market registered
4. Market resolved
5. Reward payout
6. Child comment created

V2 does not include a `notifications` router because the WebSocket user channel already delivers order/trade events in real-time. However, notifications for market resolution, reward payouts, and comments are **not** covered by the WS channel. If we add a notification bell/inbox feature, this API is the backend. The `shell/notifications-bell.tsx` component in the file tree anticipates this.

## 8. Auth & Session

This is the most structurally important change in V2.

### The Problem with localStorage Auth

The current model stores session data in Zustand persisted to `localStorage`:
- `sessionToken`, `userId`, `email`, `safeAddress`, `hasCredentials` — all in `wallet-storage`
- Page load reads localStorage → hydrates Zustand → makes requests

This creates bugs:
- Server revokes session → localStorage still says user is logged in → requests fail silently
- Tab A logs out → Tab B still thinks user is logged in (no broadcast)
- Rehydration timing → AuthGuard may flash wrong state before Zustand hydrates
- The `session-cookie-sync` component exists specifically to paper over the mismatch

### V2 Session Model

**Ground truth:** the HttpOnly JWT cookie (`/api/session` already sets this).

**Client representation:** a single TanStack Query entry.

```ts
// domains/account/hooks/use-session.ts
export function useSession() {
  return useQuery({
    ...trpc.auth.me.queryOptions(),
    staleTime: 5 * 60_000,      // 5 min — session doesn't change often
    retry: false,                // 401 = not logged in, don't retry
  });
}

// Return type: Session | null | undefined
// undefined = still loading
// null      = not authenticated
// Session   = authenticated user
```

**`trpc.auth.me` procedure** (was `auth.me`) returns:
```ts
type Session = {
  userId: string;
  email: string | null;
  address: string | null;
  safeAddress: string | null;
  hasCredentials: boolean;
  authMethod: "email" | "wallet";
  signatureType: SignatureType;
};
```

**Login flow:**
1. User authenticates (Magic DID token or SIWE signature)
2. Server calls `auth.login` or `auth.walletLogin`
3. Server validates the DID token using Magic Admin SDK (see below)
4. Server sets HttpOnly JWT cookie via `res.cookie()`
5. Server returns session data
6. Client calls `queryClient.setQueryData(trpc.auth.me.queryKey(), session)` — seeds the cache immediately without a round-trip
7. AuthGuard sees `useSession().data !== null` → allows access

**Server-side DID token validation (`auth.login` handler):**
```ts
import { Magic } from "@magic-sdk/admin";
const magicAdmin = await Magic.init(env.MAGIC_SECRET_KEY);

// 1. Extract from Authorization: Bearer <token>
const didToken = magicAdmin.utils.parseAuthorizationHeader(req.headers.authorization);
// 2. Validate signature + expiry — throws SDKError on failure
//    Error codes: TokenExpired, IncorrectSignerAddress, MalformedTokenError, AudienceMismatch
await magicAdmin.token.validate(didToken);
// 3. Get user metadata (email, wallet address, issuer)
const metadata = await magicAdmin.users.getMetadataByToken(didToken);
// metadata.publicAddress  — the Magic EOA address (signer)
// metadata.email          — may be null for OAuth-only users
// metadata.issuer         — "did:ethr:0x..." — stable user identifier
```

**OAuth callback (`getRedirectResult`) address path — SDK v30+ gotcha:**
```ts
const result = await magic.oauth2.getRedirectResult();
// SDK v30.0.0+ nests the address; earlier SDKs had a flat publicAddress field
const address = result.magic.userMetadata.wallets?.ethereum?.publicAddress
             ?? result.magic.userMetadata.publicAddress; // fallback for older installs
const didToken = result.magic.idToken;
```

**Logout flow:**
1. Client calls `trpc.auth.logout.mutate()`
2. Server revokes JWT jti in `session-blocklist` table, clears cookie
3. Client calls `queryClient.clear()` — removes all cached data
4. `useSession()` returns `null` on next render → AuthGuard redirects to `/login`

**AuthGuard using the new model:**
```ts
function AuthGuard({ children }: { children: React.ReactNode }) {
  const { data: session, isPending } = useSession();
  const pathname = usePathname();

  if (isPending) return <AppShellSkeleton />;
  if (!session && !isPublicRoute(pathname)) {
    redirect(`/login?returnTo=${pathname}`);
  }
  return children;
}
```

No Zustand reads. No localStorage checks. No rehydration timing issues.

**What localStorage still holds (non-security):**
- Wallet connection: `address`, `chainId`, `signatureType` — for pre-filling the reconnect prompt
- User preferences: `hideBalances`, dock layout, order form defaults
- Nothing security-sensitive, nothing that gates route access

### Credential Derivation

CLOB API credentials (API key, secret, passphrase) are derived deterministically from the Magic signer + Safe address. They can be re-derived at any time on the client without a server round-trip.

**L1 vs L2 CLOB methods:**

The CLOB client exposes two tiers:
- **L1 methods** — require only a wallet signer (no API credentials). Used for one-time setup: `createApiKey`, `deriveApiKey`, `getApiKeys`. The client calls these during the Safe onboarding flow.
- **L2 methods** — require derived API credentials (key + secret + passphrase). Used for all trading operations: `postOrder`, `cancelOrder`, `getOrders`, etc. Credentials must be loaded before any trade can be placed.

This distinction matters for the server: L1 calls happen once at onboarding and write the `hasCredentials: true` flag to the session. After that, only L2 calls happen, and they're client-derived, not server-stored.

**V2 credential model — client-side only:**
```ts
// domains/account/services/credentials.ts
// In-memory cache, cleared on tab close
const credentialCache = new Map<string, ClobCredentials>();

export async function getCredentials(magic: MagicBase, safeAddress: string): Promise<ClobCredentials> {
  const cached = credentialCache.get(safeAddress);
  if (cached) return cached;

  // Uses L1 method (wallet signer only) to derive API credentials deterministically
  const creds = await deriveCredentialsL1(magic, safeAddress);
  credentialCache.set(safeAddress, creds);
  return creds;
}

export function clearCredentialCache(): void {
  credentialCache.clear();
}
```

**EOA vs Safe — signer vs maker:**
- **Magic EOA** (`metadata.publicAddress`) — signs orders. This is the cryptographic identity.
- **Gnosis Safe** (`safeAddress`) — the `maker_address` in every CLOB order. This is where pUSD is held and where trades settle. All funds must be in the Safe, not the EOA.

The CLOB client is initialized with the EOA signer but configured with the Safe as the maker address. Both are required for order placement.

`trpc.auth.storeCredentials` and `trpc.auth.getCredentials` procedures are **removed**. The server never sees plaintext credentials. The credential encryption key (`CREDENTIAL_ENCRYPTION_KEY`) env var is no longer needed.

**Selector rules:**

```ts
// ✅ Atomic picks — reference-stable, no extra work needed
const address = useWalletStore((s) => s.address);
const chainId = useWalletStore((s) => s.chainId);

// ✅ Multi-pick object — use useShallow to prevent re-renders on same-value updates
import { useShallow } from "zustand/react/shallow";
const { address, chainId } = useWalletStore(
  useShallow((s) => ({ address: s.address, chainId: s.chainId }))
);

// ❌ Creates a new object every render → component re-renders on every store update
const { address, chainId } = useWalletStore((s) => ({ address: s.address, chainId: s.chainId }));

// ❌ Never derive arrays/objects inline — new reference every call
const openIds = useOrderFormStore((s) => s.pendingIds.filter(Boolean));
// ✅ Define the selector at module level, or use useMemo
const selectPendingIds = (s: OrderFormStore) => s.pendingIds.filter(Boolean);
```

`useShallow` does a shallow equality check (compares top-level keys). For deeply nested comparisons, define the equality function manually.

**Removed from the store layer entirely:**
- `useOrdersStore` → `useQuery(trpc.orders.open.queryOptions(...))`
- `usePositionsStore` → `useQuery(trpc.portfolio.positions.queryOptions(...))`
- `useOrderbookStore` → `useQuery(trpc.markets.orderbook.queryOptions(...))` + WS subscription
- `useWalletStore.sessionToken` → `useSession().data`
- `useConnectionStore` → state derived from WS hub connection events → QueryClient metadata

### Post-Trade Invalidation

When a trade executes, certain queries need refreshing. Instead of the current scattered `invalidateRealtimeQueriesWithRetry` calls, V2 uses a single post-trade hook:

```ts
// domains/trading/hooks/use-post-trade-invalidation.ts
export function usePostTradeInvalidation() {
  const queryClient = useQueryClient();

  return useCallback((scope: PostTradeScope = "full") => {
    const keys = resolveInvalidationKeys(scope);
    // Fire immediately + at 3s, 8s, 15s, 30s for slow Data API indexing
    for (const delay of [0, 3000, 8000, 15000, 30000]) {
      setTimeout(() => {
        for (const key of keys) queryClient.invalidateQueries({ queryKey: key });
      }, delay);
    }
  }, [queryClient]);
}
```

### `useMutationState` — Eliminates `pendingTradesStore` (TanStack Query v5)

TanStack Query v5's `useMutationState` tracks in-flight mutations globally without a separate Zustand store. This replaces the `pendingTradesStore` (balance deltas, position tokens, cash balance pulse) with built-in infrastructure:

```tsx
import { useMutationState } from "@tanstack/react-query";

// Show pending orders with visual indicator — no Zustand, no prop drilling
function OpenOrders() {
  const pendingOrders = useMutationState({
    filters: { mutationKey: ["orders", "place"], status: "pending" },
    select: (mutation) => mutation.state.variables,
  });

  return (
    <>
      {confirmedOrders.map(order => <OrderRow key={order.id} order={order} />)}
      {pendingOrders.map((vars, i) => (
        <OrderRow key={`pending-${i}`} order={vars} className="opacity-50" />
      ))}

// Global loading indicator for any trade in progress
function TradeActivityIndicator() {
  const pendingTrades = useMutationState({
    filters: { mutationKey: ["orders"], status: "pending" },

  return <Spinner />;

```

This means `pendingTradesStore` (currently 3 separate stores: `cash-balance-pulse-store`, `pending-balance-deltas`, `pending-position-tokens`) can be replaced by `useMutationState` queries. The "Five stores" in §9 becomes four — `pendingTradesStore` is no longer needed.

## 10. Real-Time Architecture

### Hub Design

One unified hub manages all WebSocket connections. Components never subscribe to WebSocket events directly — they read from TanStack Query, and the hub keeps that cache fresh.

```ts
// lib/ws/hub.ts

type Subscription =
  | { channel: "market"; tokenIds: string[] }
  | { channel: "user"; conditionIds?: string[] }
  | { channel: "rtds"; topics: RtdsTopic[] }
  | { channel: "sports" };

interface WsHub {
  subscribe(sub: Subscription, handler: (msg: WsMessage) => void): () => void;
  getConnectionState(): "connected" | "connecting" | "disconnected";
  onConnectionChange(handler: (state: ConnectionState) => void): () => void;
}

export const wsHub: WsHub = createWsHub();
```

**Connection topology:**
- `market` and `user` channels → one WebSocket to CLOB host (multiplexed, auth injected per subscription)
- `rtds` → separate WebSocket to RTDS host
- `sports` → separate WebSocket to Sports host

This reduces connections from 4 to 3, and more importantly ensures the authenticated user channel doesn't race with the public market channel.

### The Two Integration Patterns

**Pattern A: Snapshot + Delta** (orderbook, prices)

Initial data from REST. WebSocket applies deltas to the same query cache entry.

```ts
// lib/ws/hooks/use-market-sync.ts
export function useMarketSync(tokenId: string | null) {
  const queryClient = useQueryClient();

  useEffect(() => {
    if (!tokenId) return;
    return wsHub.subscribe({ channel: "market", tokenIds: [tokenId] }, (msg) => {
      switch (msg.type) {
        case "book":
          queryClient.setQueryData(
            trpc.markets.orderbook.queryKey({ tokenId }),
            (prev) => applyBookSnapshot(prev, msg),
          );
          break;
        case "price_change":
          queryClient.setQueryData(
            trpc.markets.orderbook.queryKey({ tokenId }),
            (prev) => applyPriceDelta(prev, msg),
          );
          break;
        case "last_trade_price":
          queryClient.setQueryData(
            trpc.markets.orderbook.queryKey({ tokenId }),
            (prev) => ({ ...prev, lastTradePrice: msg.price }),
          );
          break;
        case "market_resolved":
          // Invalidate market data so it refetches with resolved status
          queryClient.invalidateQueries({
            queryKey: trpc.markets.getBySlug.queryKey(),
          });
          break;
      }
    });
  }, [tokenId, queryClient]);
}
```

Called once from the trading page, not from `<OrderBook />`. The `<OrderBook />` component just reads the query:
```tsx
const { data: book } = useQuery(trpc.markets.orderbook.queryOptions({ tokenId }));
```

**Pattern B: Merge + Invalidate** (orders, positions)

WebSocket event arrives → merge specific record into open orders cache OR invalidate + refetch.

```ts
// lib/ws/hooks/use-account-sync.ts
export function useAccountSync(address: string | null, conditionIds?: string[]) {
  const queryClient = useQueryClient();

  useEffect(() => {
    if (!address) return;
    return wsHub.subscribe({ channel: "user", conditionIds }, (msg) => {
      switch (msg.type) {
        case "order":
          // Merge order event into the open orders query cache
          queryClient.setQueryData(
            trpc.orders.open.queryKey({ address }),
            (prev) => mergeOrderEvent(prev, msg),
          );
          // If terminal state (FILLED, CANCELLED), also refresh portfolio
          if (isTerminalOrderState(msg.status)) {
            queryClient.invalidateQueries({
              queryKey: trpc.portfolio.positions.queryKey({ address }),
            });
          }
          break;
        case "balance_update":
          queryClient.invalidateQueries({
            queryKey: trpc.portfolio.balances.queryKey({ address }),
          });
          break;
      }
    });
  }, [address, conditionIds?.join(","), queryClient]);
}
```

### Sync Hooks Are Called Once, High in the Tree

Both `useMarketSync` and `useAccountSync` are called at the page/layout level — not inside individual components. This is explicit about where subscriptions live:

```tsx
// app/(app)/market/[slug]/market-page-container.tsx

}
```

### WebSocket Best Practices (audit: 2026-04-29)

Researched against websocket.org production guides, trading platform patterns (Binance, Coinbase), and the npm package landscape. Conclusion: **no new packages needed** — the custom `WebSocketManager` is already better than generic libraries because it handles Polymarket's specific protocol (text PING/PONG, subscription messages, auth injection). Generic packages like `partysocket` (~700K/wk, best-in-class reconnecting WS) would only replace the reconnection plumbing, which is the simplest part of what we've built.

**Packages evaluated and rejected:**

| Package | Status | Why not |
|---------|--------|---------|
| `partysocket` | Active, 700K/wk | Drop-in `WebSocket` replacement. Doesn't help with Polymarket's subscription protocol, auth, or multi-channel management. We'd still need all custom logic on top. |
| `reconnecting-websocket` | Dead (last publish 2020) | `partysocket` is a fork of this with bugfixes. |
| `react-use-websocket` | Active, 150K/wk | Couples WS lifecycle to component lifecycle — exactly what §12F says NOT to do. |
| `socket.io-client` | Active, 4M/wk | Requires Socket.IO server. Polymarket uses raw WS. Massive overhead. |

**Improvements to apply to the existing `WebSocketManager`:**

**1. Widen jitter range (1 line).** Current ±25% (`0.75 + Math.random() * 0.5`) clusters reconnects too tightly. Change to 50–100% (`0.5 + Math.random() * 0.5`) for better thundering herd prevention when Polymarket's WS server restarts.

**2. Add max retry limit.** Current manager retries forever. Add a cap at 12 attempts (~2 min with the backoff curve), then surface a "disconnected" state. Prevents infinite retry on mobile (battery drain) and against a truly-down server. Let the user trigger manual reconnect after giving up.

**3. REST snapshot on reconnect (most important).** When the WS reconnects, there's a gap — messages were sent while offline. The industry-standard pattern (Binance, Coinbase, all orderbook systems) is: reconnect → re-subscribe → **immediately fetch a REST snapshot** → apply to cache → resume deltas. The `onReconnect` callback exists but isn't consistently used. V2's sync hooks should invalidate the relevant TanStack Query on reconnect:

```ts
// use-market-sync.ts — on reconnect, fill the data gap
onReconnect: () => {
  queryClient.invalidateQueries({
    queryKey: trpc.markets.orderbook.queryKey({ tokenId }),
  });
}
```

**4. Connection state via `useSyncExternalStore`.** Instead of a Zustand store for WS connection state, use React's built-in external store hook — the hub already exposes `getConnectionState()` and `onConnectionChange()`, which is exactly the `useSyncExternalStore` contract:

```ts
const connectionState = useSyncExternalStore(
  wsHub.onConnectionChange,
  wsHub.getConnectionState,
);
```

**5. Already correct (confirmed by research):**
- Zod validation on every inbound message (schemas.ts, sports-schemas.ts) — explicitly called out as a best practice
- Subscription set tracking + re-subscribe on reconnect — correct buffering pattern
- Heartbeat with 30s timeout detection — matches industry standard
- Sentry metrics on connect/disconnect/failures — good observability
- Connection lives in layout, not page components — prevents connection churn

### Chart Architecture Notes

The `trading/components/chart/` directory has five internal layers. Never import across layer boundaries except through `chart/index.ts`.

#### Layer Map

| Layer | Directory | What lives here |
|-------|-----------|-----------------|
| **Entry** | `components/` | `chart-slot.tsx` (public API), `kline-chart.tsx` (outer shell), `kline-chart-inner.tsx` (KLineChart instance), `kline-toolbar.tsx`, `legend-bar.tsx` |
| **All-markets overlay** | `all-markets/` | Separate `<canvas>` renderer for multi-outcome price lines — completely independent of KLineChart |
| **KLineChart config** | `config/` | Styles, Y-axis range callback, drawing tool overlay templates (Apache 2.0 port from klinecharts/pro) |
| **Data** | `data/` | CLOB fetch (fidelity ladder + max/all merge), OHLC bar loading (init/forward paging), aggregation/bucketing, interval constants |
| **Hooks** | `hooks/` | `use-trade-markers.ts` — user trade query → annotation overlays |

#### Component Responsibilities

**`chart-slot.tsx`** — Thin public entry point. Just renders `<PolymarketKLineChart>`. Consumers import from here, not from `kline-chart.tsx` directly.

**`kline-chart.tsx`** — Outer shell. Owns: interval + chart-type state (from `workspaceLayoutStore`), drawing tool state (`activeTool`, `selectedOverlayId`), all-markets mode switch, initial data hydration from `initialData` prop (server-prefetched), toolbar rendering. Uses `next/dynamic` with `ssr: false` to lazy-load `kline-chart-inner.tsx`. Has `"use no memo"` directive to opt out of React Compiler.

**`kline-chart-inner.tsx`** — KLineChart v10 instance. Owns six `useEffect`s:
1. Chart lifecycle (init, `ResizeObserver`, dispose) — reruns on theme change only
2. Data loader + WS subscription (`loadPolymarketKlineBars` + `marketChannel`) — reruns on tokenId/assetIds
3. Interval change → `chart.setPeriod()`
4. Chart type/theme sync → `chart.setStyles()`
5. Resolution overlay — "Resolved" annotation for closed markets
6. Sonar ring — live price dot tracking via RAF after scroll/zoom/WS bar updates

**`all-markets-line-layer.tsx`** — Entirely independent canvas-based multi-outcome chart. Renders on a `<canvas>` absolutely positioned over the KLineChart container. Has its own fetch logic, WS subscription via `marketChannel`, pan/zoom pointer handlers, and crosshair drawing. Does NOT use KLineChart APIs.

#### Critical Data Flow

```
Server (RSC)
  └─ prefetchQuery(trpc.clob.getPricesHistory, "max")  ← seeds initialData prop
       │
Client hydration
  └─ kline-chart.tsx receives initialData
       └─ passes seedForMax to kline-chart-inner.tsx
            └─ loadPolymarketKlineBars({ loadType: "init", seedForMax })
                 └─ skips API call if seedForMax has points → zero network waterfall on load
```

The `seedForMax` pattern is how we avoid a waterfall: the RSC prefetches `max` history, passes it as a prop, and the chart uses it directly instead of fetching again on mount.

#### Fetch Strategy by Interval

| Interval | Source | Paging |
|----------|--------|--------|
| `max` / `1d` / `1w` / `1m` | `fetchWideHistoryMergedMaxAndAll` (both CLOB presets merged) | One-shot — no forward/backward |
| `1h` / `15m` / `1min` | `fetchExplicitRangeWithLadder` (explicit `startTs`/`endTs`) | Paged: init = last 7d; forward = older 7d chunks on scroll |

The fidelity ladder retries with coarser fidelity when the CLOB rejects a request. For `max`/`all` presets the ladder runs coarse-first (1440 min → 360 → …) because fine fidelity returns only a short recent window instead of full history.

#### All Markets Overlay vs KLineChart

| Feature | KLineChart (`kline-chart-inner.tsx`) | All Markets canvas (`all-markets-line-layer.tsx`) |
|---------|-------------------------------------|--------------------------------------------------|
| Mode | Single outcome (tokenId) | All outcomes in GMP event |
| Renderer | KLineChart v10 library | Raw `<canvas>` 2D context |
| Chart type | Candle / line / OHLC | Line only |
| WS | `marketChannel` (single asset) | `marketChannel` (all asset IDs) |
| Interaction | KLineChart built-in crosshair | Custom pan/zoom/crosshair |
| Shown when | `allMarketsMode === false` | `allMarketsMode === true` |

The two modes are mutually exclusive. `kline-chart.tsx` conditionally renders `AllMarketsLineLayer` over the chart canvas and hides the KLineChart toolbar when in all-markets mode.

#### Sonar Ring

The sonar ring is a CSS-animated `<div>` (doji-green circle) positioned absolutely over the KLineChart canvas at the pixel location of the last price. It repositions via `requestAnimationFrame` in response to:
- WS `last_trade_price` events (new bar appended)
- Chart scroll/zoom (coordinate mapping changes)
- Theme change (chart reinitialized)

The ring hides during pointer interaction (hover/drag) to avoid z-fighting with the crosshair. Pixel position is computed from `chart.convertToPixel({ timestamp, value })`.

## 12. Rendering Architecture

This is the section that directly addresses the class of bugs that caused the most pain in V1: hydration mismatches, stale cache, client-side waterfalls, WebSocket flickering on navigation, and PPR build failures. Every rule here was derived from a real production failure pattern.

---

### A. Client/Server Component Boundary

**The fundamental rule:** every file in `app/` is a Server Component unless it says `"use client"`. Server Components run on the server, produce no client JS, and can directly access the database or tRPC caller. Client Components run on both server (for SSR) and client (for hydration).

**When to add `"use client"` (mechanical checklist):**

| Needs | Add `"use client"`? |
|-------|---------------------|
| `useState`, `useReducer`, `useRef` | Yes |
| `useEffect`, browser APIs (`window`, `document`) | Yes |
| `useQuery`, `useMutation`, Zustand | Yes |
| Event handlers (`onClick`, `onChange`) | Yes |
| Async data fetch only | **No** — keep as Server Component |
| Rendering server-fetched props | **No** — keep as Server Component |

**Keep the boundary as small and as low in the tree as possible.** The typical pattern is a Server Component page that fetches data and passes it as props to one slim Client Component that handles interactivity:

```tsx
// ✅ Correct — Server Component fetches, slim client component reacts
// app/(app)/market/[slug]/page.tsx (Server Component)
export default async function Page({ params }) {
  const caller = await trpc();
  const market = await caller.markets.getBySlug({ slug: params.slug });
  return <MarketPageContainer market={market} />;
}

// domains/trading/components/market-page-container.tsx ("use client")
"use client";
export function MarketPageContainer({ market }: { market: Market }) {
  useMarketSync(market.yesToken);          // WS subscription
  useAccountSync(session?.address ?? null);
  return <TradingLayout market={market} />;
}

// ❌ Wrong — fetching in a Client Component means client-side waterfall
"use client";
export function MarketPage({ slug }: { slug: string }) {
  const { data: market } = useQuery(trpc.markets.getBySlug.queryOptions({ slug }));
  ...
}
```

**Functions cannot cross the Server → Client boundary as props.** React serializes props when handing off from server to client. Functions are not serializable. The error is `Functions cannot be passed directly to Client Components`.

```tsx
// ❌ Runtime error
<ClientButton onClick={serverSideFunction} />

// ✅ Mark it as a Server Action, or define the handler inside the Client Component
```

**Children of Client Components can be Server Components.** Pass Server Components as `children` — they are resolved on the server before the client component receives them. This lets you keep interactive wrappers thin:

```tsx
// ✅ Counter is "use client", but StaticContent stays a Server Component
<Counter>
  <StaticContent />   {/* Server Component — no client JS */}
</Counter>
```

**Context providers must be Client Components.** Wrap in a `"use client"` provider that takes `children`, not the root layout itself:

```tsx
// ✅
"use client";
export function QueryProvider({ children }: { children: React.ReactNode }) {
  const [client] = useState(() => makeQueryClient());
  return <QueryClientProvider client={client}>{children}</QueryClientProvider>;
}
```

### B. Data Fetching — Eliminating Waterfalls

A **waterfall** is when request B can't start until request A finishes. They are almost always avoidable.

**Rule 1: Never call a Route Handler from a Server Component.**

```tsx
// ❌ Creates a loopback HTTP request — RSC → Route Handler → DB
const res = await fetch("http://localhost:3000/api/data");

// ✅ Call the function or tRPC caller directly
const caller = await trpc();
const data = await caller.markets.list({});
```

**Rule 2: Fetch in parallel — always.**

```tsx
// ❌ Sequential — market fetches first, orderbook can't start until it's done
const market = await caller.markets.getBySlug({ slug });
const book = await caller.markets.orderbook({ tokenId: market.yesToken });

// ✅ Parallel where possible
const [market, topMarkets] = await Promise.all([
  caller.markets.getBySlug({ slug }),
  caller.markets.list({ limit: 5 }),
]);
// Dependent fetch is acceptable when it truly depends on the first result
const book = await caller.markets.orderbook({ tokenId: market.yesToken });
```

**Rule 3: Use `React.cache()` to deduplicate shared fetches.**

When `generateMetadata` and the `page` component both need the same data, wrap the fetcher in `React.cache()`. Next.js calls both in parallel, but `React.cache()` ensures only one DB round-trip happens:

```tsx
// lib/data/get-market.ts
import { cache } from "react";
export const getMarket = cache(async (slug: string) => {
  const caller = await trpc();
  return caller.markets.getBySlug({ slug });
});

// app/market/[slug]/page.tsx
export async function generateMetadata({ params }) {
  const market = await getMarket(params.slug); // deduped
  return { title: market.question };
}
export default async function Page({ params }) {
  const market = await getMarket(params.slug); // same promise — no second fetch
  ...
}
```

**Rule 4: Prefetch TanStack Query from RSC — don't let the client refetch.**

```tsx
// app/(app)/market/[slug]/page.tsx
import { dehydrate, HydrationBoundary } from "@tanstack/react-query";

export default async function Page({ params }) {
  const qc = makeQueryClient();
  // Start fetch without awaiting — stream to client as it resolves
  void qc.prefetchQuery(trpc.markets.getBySlug.queryOptions({ slug: params.slug }));
  void qc.prefetchQuery(trpc.markets.orderbook.queryOptions({ tokenId }));

  return (
    <HydrationBoundary state={dehydrate(qc)}>
      <MarketPageContainer slug={params.slug} />
    </HydrationBoundary>
  );
}
```

With `shouldDehydrateQuery` configured to include pending queries, the client component picks up the in-flight promise and suspends until it resolves — no second network request:

```ts
// lib/trpc/query-client.ts
export function makeQueryClient() {
  return new QueryClient({
    defaultOptions: {
      dehydrate: {
        shouldDehydrateQuery: (query) =>
          defaultShouldDehydrateQuery(query) || query.state.status === "pending",
      },
    },
  });
}
```

**Rule 5: Don't fetch in layouts for per-request dynamic data.**

Layouts with uncached dynamic data block navigation — the user sees nothing until the layout fetch resolves. Keep layout data either:
- **Cached** with `"use cache"` (market list in the explore sidebar), or
- **Deferred** into the page with `<Suspense>` + skeleton

```tsx
// ❌ Blocks all child page navigations
export default async function Layout() {
  const user = await getUser(); // uncached, every request
  return <Sidebar user={user}>{children}</Sidebar>;
}

// ✅ Layout reads from query cache seeded by the page RSC, or defers
export default function Layout({ children }) {
  return <Sidebar>{children}</Sidebar>; // Sidebar reads useSession() client-side
}
```

### C. Caching — `"use cache"` in Next.js 16

**The model:** `cacheComponents: true` in `next.config.ts` opts in to the new cache model. Nothing is cached by default. You explicitly mark what to cache with `"use cache"`.

```ts
// next.config.ts
const config: NextConfig = {
  cacheComponents: true, // replaces experimental.ppr + experimental.dynamicIO
};
```

**What to cache vs. what not to cache:**

| Data | Cache? | Why |
|------|--------|-----|
| Public event/market listings | `"use cache"` + `cacheLife("minutes")` | Same for all users, high read volume |
| Single market detail (slug) | `"use cache"` + `cacheTag(slug)` | Invalidate on resolution |
| Orderbook snapshot | **Never** — TanStack Query | Real-time; differs per user |
| Session / user data | **Never** — TanStack Query | Per-user; cookie-gated |
| Leaderboard | `"use cache"` + `cacheLife("minutes")` | Public, can tolerate staleness |

**Cache as close to the data source as possible — not at the layout or page level:**

```tsx
// ✅ Cache the function that fetches, not the whole page
async function getEventListing(cursor?: string) {
  "use cache";
  cacheLife("minutes");
  cacheTag("events");
  return fetchGammaEvents(cursor);
}

// ❌ Caching the page means user-specific sections get incorrectly cached
export default async function Page() {
  "use cache"; // wrong — page may contain user-specific data
  ...
}
```

**`cacheTag` + `revalidateTag` for targeted invalidation:**

```ts
// Tag market cache entries by condition ID
async function getMarket(slug: string) {
  "use cache";
  cacheTag(`market:${slug}`);
  cacheLife("hours");
  return fetchMarket(slug);
}

// When a market resolves, invalidate just that entry
import { revalidateTag } from "next/cache";
revalidateTag(`market:${slug}`); // background revalidate — serves stale while refetching
```

Use `updateTag` (immediate, synchronous) only inside Server Actions. Use `revalidateTag` everywhere else.

**Multi-instance deployments:** The default `"use cache"` uses in-memory storage. If running multiple Vercel instances (scale-out), add a remote cache handler (Redis/Upstash) so invalidations propagate across instances. For a single-region Vercel deployment this is not needed initially.

### D. Suspense — Boundaries, Placement, Skeletons

**Rule: the `<Suspense>` boundary must be ABOVE the async component, never inside it.**

```tsx
// ✅ Correct — Suspense wraps the component doing the async work
export default function Page() {
  return (
    <Suspense fallback={<OrderbookSkeleton />}>
      <OrderBook tokenId={tokenId} />
    </Suspense>
  );
}

// ❌ Wrong — boundary inside the async component; it never activates
export default async function OrderBook({ tokenId }) {
  return (
    <Suspense fallback={<Spinner />}>   {/* inside the async component */}
      {await fetchOrderbook(tokenId)}
    </Suspense>
  );
}
```

**Granularity rule:** one `<Suspense>` per independently-loading data slice. For the trading page: orderbook, chart, and order history load independently → three boundaries. Don't wrap the entire trading layout in one boundary — the user can't see *any* content until the slowest data source resolves.

```tsx
// Trading page — three independent data regions, three boundaries
export default function TradingPage({ market }) {
  return (
    <div className="trading-layout">
      <Suspense fallback={<OrderbookSkeleton />}>
        <OrderBook tokenId={market.yesToken} />
      </Suspense>
      <Suspense fallback={<ChartSkeleton />}>
        <PriceChart conditionId={market.conditionId} />
      </Suspense>
      <Suspense fallback={<OrdersSkeleton />}>
        <OpenOrders conditionId={market.conditionId} />
      </Suspense>
    </div>
  );
}
```

**Skeleton dimensions must match content to prevent CLS.** Use `min-h-[Npx]` or fixed-height containers on skeleton components so the space is reserved before content arrives. A skeleton with the wrong height causes a layout shift when the real component renders.

**`loading.tsx` vs manual `<Suspense>`:**

| Situation | Use |
|-----------|-----|
| Entire route has one loading state | `loading.tsx` |
| Page has multiple independent sections | Manual `<Suspense>` in the page component |
| Section loads independently of the page | Manual `<Suspense>` wrapping the section |
| PPR static shell with one dynamic island | Single `<Suspense>` around only the dynamic part |

**Don't overdo it.** Not every component needs a Suspense boundary. Only add one where you want a distinct loading sequence. A skeleton per component is noise; a skeleton per independently-loaded section is UX.

### E. PPR — `cacheComponents` and the `Date.now()` Problem

With `cacheComponents: true`, Next.js pre-renders everything it can at build time. Any uncached `Date.now()` call during the prerender pass fails with:

> `Cannot access Date.now() before other uncached data in a Server Component`

**Root cause in Doji V1:** `QueryClient` calls `Date.now()` internally during initialization. Creating a `QueryClient` in an RSC without calling `connection()` first causes this error.

**Fix — always `await connection()` before creating `QueryClient` in RSC:**

```tsx
// app/(app)/market/[slug]/page.tsx
import { connection } from "next/server";

export default async function Page({ params }) {
  await connection(); // signals: this component is dynamic, skip prerender
  // Now safe to create QueryClient (which calls Date.now() internally)
  const qc = makeQueryClient();
  ...
}
```

**`connection()` requires a `<Suspense>` boundary somewhere above it in the tree.** Without it, the entire route becomes blocking-dynamic. The boundary tells PPR where to cut between the static shell and the dynamic island.

**`"use cache"` functions are still static from PPR's perspective.** They satisfy caching but do NOT count as "dynamic data access." Only `connection()`, `cookies()`, `headers()`, or `searchParams` access make a component dynamic for PPR purposes.

### F. WebSocket Lifecycle in Next.js

WebSocket connections in Next.js must follow strict placement rules or they will be created on every navigation, leak connections, and cause flickering.

**Rule 1: WebSocket setup belongs in `useEffect`, never at module scope.**

```tsx
// ❌ Crashes during SSR — window.WebSocket doesn't exist on the server
const ws = new WebSocket("wss://...");

// ✅ Client-only, runs after mount
useEffect(() => {
  const ws = new WebSocket("wss://...");
  return () => ws.close();
}, []);
```

**Rule 2: The hub provider lives in a layout, not a page.**

If the hub is mounted inside a page component, it disconnects and reconnects on every navigation. Lift it to the `(app)/layout.tsx` so it persists for the entire authenticated session:

```tsx
// app/(app)/layout.tsx
"use client";
export default function ShellLayout({ children }) {
  // Hub initializes once, persists across /explore, /market/*, /portfolio, etc.
  useWsHubLifecycle();
  return <>{children}</>;
}
```

**Rule 3: Individual sync hooks (`useMarketSync`, `useAccountSync`) live in page containers, not in leaf components.**

The hub manages connections; sync hooks manage which data to subscribe to. A sync hook in `<OrderBook />` would create N subscriptions if `<OrderBook />` is mounted N times:

```tsx
// ✅ One subscription per page
function MarketPageContainer({ market }) {
  useMarketSync(market.yesToken);   // subscribes once for this page
  return <TradingLayout market={market} />;
}

// ❌ Each instance creates its own subscription
function OrderBook({ tokenId }) {
  useMarketSync(tokenId); // creates a subscription per orderbook component
  ...
}
```

**Rule 4: Vercel cannot host persistent WebSocket servers.** Our WebSocket connections go to the Hono server (separate Vercel project or fly.io deployment) — not to Next.js Route Handlers. Route Handlers on Vercel run as serverless functions and terminate after the response. The Hono server is the correct WebSocket host. This is already correct in V2 architecture — don't be tempted to add `/api/ws/route.ts`.

### G. Route Prefetching

Two layers of prefetching work together:

**Layer 1: Next.js `<Link>` prefetching** — prefetches the RSC shell (HTML) when the link enters the viewport or on hover. This is automatic and built in.

**Layer 2: TanStack Query data prefetching** — prefetches the actual data on hover, so when the user navigates the data is already warm in the cache:

```tsx
// domains/explore/components/event-card.tsx
"use client";
export function EventCard({ event }: { event: Event }) {
  const queryClient = useQueryClient();

  return (
    <Link
      href={`/event/${event.slug}`}
      onMouseEnter={() => {
        // Prefetch the market data for this event on hover
        void queryClient.prefetchQuery(
          trpc.events.getBySlug.queryOptions({ slug: event.slug })
        );
      }}
    >
      {event.title}
    </Link>
  );
}
```

Combine this with the RSC `prefetchQuery` at the page level for the canonical "instant navigation" experience: user hovers → data starts loading → user clicks → data is already there.

**Don't over-prefetch.** Only prefetch data the user is likely to need (hover intent is a strong signal). Prefetching every visible card on mount is a DoS against the API.

### H. When to Use `layout.tsx`

A layout does not re-render on child navigation — React preserves its DOM and state. The page swaps; the layout stays. That is both its power and its footgun.

**Use `layout.tsx` for:**

| Use case | Example |
|----------|---------|
| Root providers + `<html><body>` | `app/layout.tsx` — mandatory |
| Persistent shell UI that spans all routes | `(app)/layout.tsx` — header, nav, dock, WS hub |
| Unauthenticated shell | `(auth)/layout.tsx` — no header/nav |
| A tab bar that persists across genuinely separate child routes | `portfolio/layout.tsx` if portfolio has `/portfolio`, `/portfolio/positions`, `/portfolio/history` as separate routes |
| Metadata title templates | `export const metadata = { title: { template: '%s \| Doji' } }` |

**Never use `layout.tsx` for:**

**Uncached data fetches.** This is the silent nav-blocking bug. `loading.tsx` sits *below* `layout.tsx` — it cannot show a fallback for data access in the layout. Any uncached `await` in a layout blocks every child navigation with no loading feedback:

```tsx
// ❌ Blocks every navigation to every child page — loading.tsx never shows
export default async function ExploreLayout({ children }) {
  const featured = await getFeaturedEvents(); // uncached
  return <ExploreShell featured={featured}>{children}</ExploreShell>;
}

// ✅ Layout is structural only. Page prefetches its own data.
export default function ExploreLayout({ children }) {
  return <>{children}</>;  // no layout needed at all — delete this file
}
```

**Single-page routes with no sub-routes.** If there are no child routes sharing persistent UI, a `layout.tsx` is an empty file that adds noise. Delete it. This is why `/explore`, `/leaderboard`, `/watchlist`, `/bridge`, and `/referrals` have no layout in V2 — each is a single page.

**Shared data across child pages.** Use `React.cache()` in each page's RSC instead. It deduplicates across `generateMetadata` + `page` within a single render pass — no blocking, no layout needed.

**The quick check:** If you remove the layout and the UI still works — delete the layout.

### I. The "Forbidden" Patterns Reference Card

A single reference for patterns that cause build failures, runtime crashes, or silent data bugs:

| Pattern | Why it fails | Fix |
|---------|-------------|-----|
| `fetch('/api/...')` from Server Component | Loopback HTTP, extra latency | Call the function directly |
| Sequential `await` for independent data | Waterfall | `Promise.all([...])` |
| `"use client"` at the top of a layout | Marks entire route tree as client JS | Move `"use client"` to the smallest needed component |
| Functions as props from Server → Client | Not serializable — runtime error | Use Server Actions or define handler in Client Component |
| `Date.now()` in RSC without `connection()` | PPR prerender crash | `await connection()` first, inside a `<Suspense>` |
| `QueryClient` in RSC without `connection()` | Same — QueryClient calls Date.now() | `await connection()` before `makeQueryClient()` |
| `<Suspense>` inside the async component | Boundary never activates | Move Suspense to the parent |
| `redirect()`/`notFound()` inside try/catch | Throws a special Next.js error, gets swallowed | Call outside try/catch, or use `unstable_rethrow()` |
| WebSocket at module scope | Crashes SSR | Move to `useEffect` |
| WS hub in page component | Reconnects on every navigation | Move to layout |
| `"use cache"` on a page with user data | Caches personal data for all users | Only cache genuinely public data; use TanStack Query for personal data |
| `unstable_cache` in new code | Deprecated in Next.js 16 | Use `"use cache"` + `cacheLife()` |
| Fetching in layout without caching | Blocks page navigation | Cache or defer to page |
| `useSearchParams()` without `<Suspense>` | Silently degrades entire page to CSR | Always wrap in Suspense boundary |
| Passing `Date` objects across RSC→client boundary | Silently serializes to string, crashes on `.getFullYear()` | Use `.toISOString()` on server, `new Date(iso)` on client |
| Serializing full Gamma market object to client | 50+ fields in HTML payload, most unused | Pick only the fields the client component needs |
| `middleware.ts` in Next.js 16 | Renamed to `proxy.ts` with `proxy()` export | Run `npx @next/codemod@latest upgrade` to auto-rename |

### J. Loading States, Skeletons & the Static-First Hierarchy

The goal is not to make loading states look good. The goal is to minimize how much of the page ever needs a loading state in the first place. Skeletons are a last resort — the first strategy is to make the content genuinely instant.

#### The Four Tiers of Content Speed

Every piece of UI falls into one of four tiers. The tier determines whether you need a skeleton at all:

| Tier | What it is | Loading state needed? |
|------|-----------|----------------------|
| **Static shell** | Layout, nav, headings, anything in the prerendered HTML | Never — already there |
| **Cached public data** | Event listings, market metadata cached with `"use cache"` | Almost never — arrives in the static HTML |
| **Streamed fresh data** | Personal orders, balances, live prices behind `<Suspense>` | Yes — skeleton replaces this region while streaming |
| **Client-only data** | Data fetched in a Client Component after hydration | Yes, but also consider moving to Tier 2 or 3 |

**The first question when designing any page is: which tier does each piece of content belong to?** Then you only add skeletons for Tiers 3 and 4.

---

#### What Should NEVER Show a Skeleton

These are things that belong in the static shell and should arrive pre-rendered, not behind a Suspense boundary:

- Page header, site nav, bottom bar — never a skeleton
- Event/market title and description — cache these with `"use cache"`; they're in the HTML by the time the browser paints
- The layout/chrome of the trading terminal — the structure itself (panels, column headers, labels) should be visible immediately; only the **data rows** stream in
- The order form inputs (side selector, order type tabs, labels) — render statically; only the price input value and balance amount are dynamic
- Category labels, tab bars, breadcrumbs — always static

If the user sees a skeleton where a structural element could have been pre-rendered, that's a missed caching opportunity, not a necessary loading state.

---

#### Choosing the Right Tool: `loading.tsx` vs `<Suspense>` vs `<Activity>`

These three tools solve fundamentally different problems:

**`loading.tsx` — route-level shell while the page streams in:**

Next.js automatically wraps `page.tsx` in a Suspense boundary and uses `loading.tsx` as the fallback. The loading state is **prefetched** along with the route — meaning when the user clicks a link, the loading skeleton appears instantly (no blank screen, no FOUC) while the actual page data streams in.

```
app/(app)/portfolio/
  page.tsx         # the real page — streams in
  loading.tsx      # prefetched skeleton — shown instantly on navigation
```

Use `loading.tsx` when:
- The entire page content is dynamic/personal (portfolio, orders, watchlist)
- You want an instant visual response on navigation without any code in `page.tsx`
- The page-level skeleton is a reasonable single chunk

Do NOT use `loading.tsx` when:
- Some parts of the page are static — those parts would be hidden behind the skeleton unnecessarily
- You need different regions to stream in at different speeds
- The page has a rich layout that can be pre-rendered (use PPR + manual `<Suspense>` instead)

---

**`<Suspense>` — independent streaming regions within a page:**

Wrap only the component that does the async fetch. Everything outside that boundary renders immediately (from cache or static shell).

```tsx
// The structural layout renders immediately.
// Only the dynamic data regions are behind Suspense.
export default function TradingPage({ market }) {
  return (
    <TradingLayout>              {/* renders instantly — static structure */}
      <Suspense fallback={<OrderbookRowsSkeleton />}>
        <OrderbookRows tokenId={market.yesToken} />   {/* streams in */}
      </Suspense>

      <Suspense fallback={<OpenOrdersRowsSkeleton />}>
        <OpenOrdersRows conditionId={market.conditionId} />
      </Suspense>

      <Suspense fallback={<BalanceSkeleton />}>
        <WalletBalance />
      </Suspense>
    </TradingLayout>
  );
}
```

Notice: `<TradingLayout>` itself renders immediately. The column headers, spread bar, order form shell — all visible. Only the **rows** and **balance** are behind skeletons.

---

**`<Activity>` — toggling visibility without unmounting (tabs, panels):**

`<Activity mode="visible" | "hidden">` is the correct tool for tabs, dock panels, and any UI that toggles between shown/hidden states. It:

- **Preserves state** — a user's typed order size survives switching to the positions tab and back
- **Continues background fetching** — hidden panels prefetch their data at low priority; when they become visible, the data is already there
- **Does NOT show a fallback** — a suspended component inside a hidden `<Activity>` waits silently in the background, no skeleton in the viewport

```tsx
// Market page tab switcher — Activity preserves state, preloads in background
function MarketTabs({ tab, conditionId }: { tab: Tab; conditionId: string }) {
  return (
    <>
      <Activity mode={tab === "orderbook" ? "visible" : "hidden"}>
        <OrderbookPanel conditionId={conditionId} />
      </Activity>
      <Activity mode={tab === "positions" ? "visible" : "hidden"}>
        <PositionsPanel conditionId={conditionId} />
      </Activity>
      <Activity mode={tab === "activity" ? "visible" : "hidden"}>
        <ActivityPanel conditionId={conditionId} />
      </Activity>
    </>
  );
}
```

Do NOT use conditional rendering (`{tab === "x" && <X />}`) for panels that have their own data — the component unmounts and remounts on every tab switch, losing state and re-fetching.

---

**`startTransition` — refresh without reverting to skeleton:**

When the user changes a filter, sorts a table, or navigates between pages within a section, you do NOT want the Suspense fallback to re-appear (that's a regression — the user had real content, now it's gone). Use `startTransition` to keep showing the stale result while the fresh data loads:

```tsx
"use client";
function MarketFilter({ markets }: { markets: Market[] }) {
  const [filter, setFilter] = useState("all");
  const [isPending, startTransition] = useTransition();

  return (
    <>
      <FilterBar
        value={filter}
        onChange={(v) => startTransition(() => setFilter(v))}
      />
      {/* isPending = true while new data loads — dim instead of skeleton */}
      <div style={{ opacity: isPending ? 0.6 : 1, transition: "opacity 200ms" }}>
        <MarketList filter={filter} />
      </div>
    </>
  );
}
```

The existing UI stays visible but dimmed. A subtle transition communicates "loading new results" without destroying the layout. Use this for: sort/filter changes, pagination, tab switching when data changes but layout doesn't.

#### Skeleton Anatomy Rules

A skeleton that doesn't match the final content causes layout shift (bad CLS score, jarring UX). A skeleton that matches exactly looks invisible — the content "appears in place" rather than "popping in".

**Rule 1: Skeletons live in the same layout as real content.**

The skeleton and the real component should share their outer container, padding, and height:

```tsx
// ✅ Skeleton is the same height as the real row — no shift on resolution
function OrderRowSkeleton() {
  return (
    <div className="grid grid-cols-[1fr_1fr_80px_100px] h-[32px] items-center px-3 gap-2">
      <Skeleton className="h-3 w-24 rounded" />
      <Skeleton className="h-3 w-16 rounded" />
      <Skeleton className="h-3 w-12 rounded" />
      <Skeleton className="h-3 w-14 rounded" />
    </div>
  );
}

// Real row — same outer container
function OrderRow({ order }: { order: Order }) {
  return (
    <div className="grid grid-cols-[1fr_1fr_80px_100px] h-[32px] items-center px-3 gap-2">
      <span className="text-sm">{order.market}</span>
      ...
    </div>
  );
}
```

**Rule 2: Count matters — skeleton row count should match expected real count.**

A single skeleton row followed by 20 real rows shifts the layout. Render the expected number of skeleton rows (or use a fixed-height container):

```tsx
// If we expect ~10 orders, show 8 skeleton rows
function OpenOrdersSkeleton() {
  return (
    <>
      {Array.from({ length: 8 }).map((_, i) => (
        <OrderRowSkeleton key={i} />
      ))}
    </>
  );
}
```

**Rule 3: Don't skeleton the chrome — only the data.**

Column headers, section labels, and the overall grid structure render immediately and never show a skeleton. Only the row content (prices, amounts, market names) needs one:

```tsx
// ✅ Header is always visible. Only rows are behind Suspense.
<OrderbookPanel>
  <OrderbookHeader />                           {/* always rendered */}
  <Suspense fallback={<OrderbookRowsSkeleton />}>
    <OrderbookRows tokenId={tokenId} />         {/* streams in */}
  </Suspense>
  <SpreadBar />                                 {/* always rendered */}
</OrderbookPanel>
```

**Rule 4: Use `pulse` animation, not `shimmer`, for financial data.**

Shimmer (the left-to-right sweep) implies text and image content. Pulse (opacity in/out) is less distracting for dense numerical data like orderbooks and tables. shadcn's `<Skeleton>` component uses `animate-pulse` by default — keep it.

**Rule 5: Reserve space before you know the count.**

For sections where you don't know how many items there will be (e.g., a positions list), use a fixed-height container that reserves enough space:

```tsx
// Reserve ~300px while positions load — prevents the page shifting down
function PositionsSkeleton() {
  return (
    <div className="min-h-[300px]">
      {Array.from({ length: 5 }).map((_, i) => <PositionRowSkeleton key={i} />)}
    </div>
  );
}
```

#### The Skeleton Decision Flowchart

```
Is this content the same for all users?
  └─ Yes → Can I use "use cache"?
        └─ Yes → Cache it; it arrives in HTML; NO skeleton needed
        └─ No  → Add it to the static shell (structural chrome); NO skeleton needed
  └─ No  → Is this a layout chrome element (nav, headers, labels)?
        └─ Yes → Move it out of any Suspense boundary; NO skeleton needed
        └─ No  → Is the user already looking at real content (refresh/filter change)?
              └─ Yes → Use startTransition + opacity dim; NO skeleton
              └─ No  → Is this a tab/panel that can be pre-loaded hidden?
                    └─ Yes → Wrap with Activity; skeleton only on first show
                    └─ No  → USE A SKELETON.
                              - Skeleton shares layout with real component
                              - Same height/width
                              - Only the data cells shimmer
                              - Chrome (headers, labels) rendered outside the boundary
```

### K. JavaScript Performance Hot Paths

Rules for code that runs on every WS message, every orderbook update, or every render of a 1000-row table. These are the inner loops where micro-optimizations matter.

**Build index Maps for repeated lookups.** Convert arrays to Maps for O(1) access. Critical for orderbook processing and position-by-token lookups:

```ts
// ❌ O(n) per lookup — 1000 orders × 1000 markets = 1M ops
orders.map(o => ({ ...o, market: markets.find(m => m.conditionId === o.conditionId) }));

// ✅ O(1) per lookup — 2000 ops total
const marketById = new Map(markets.map(m => [m.conditionId, m]));
orders.map(o => ({ ...o, market: marketById.get(o.conditionId) }));
```

**Use `toSorted()` instead of `sort()`.** `.sort()` mutates in place — breaks React's immutability model. Use `.toSorted()` for orderbook levels, position lists, leaderboard rankings.

**Combine multiple array iterations.** Single-pass categorization instead of multiple `.filter()` calls:

```ts
// ❌ 3 iterations over positions
const open = positions.filter(p => p.status === "open");
const closed = positions.filter(p => p.status === "closed");
const redeemable = positions.filter(p => p.redeemable);

// ✅ 1 iteration
const open: Position[] = [], closed: Position[] = [], redeemable: Position[] = [];
for (const p of positions) {
  if (p.status === "open") open.push(p);
  if (p.status === "closed") closed.push(p);
  if (p.redeemable) redeemable.push(p);
}
```

**Narrow effect dependencies to booleans.** Derive a boolean from a continuous value to prevent effects from re-running on every tick:

```ts
// ❌ Runs on every price tick
useEffect(() => { if (price < threshold) showAlert(); }, [price]);

// ✅ Runs only when crossing the threshold
const isBelowThreshold = price < threshold;
useEffect(() => { if (isBelowThreshold) showAlert(); }, [isBelowThreshold]);
```

**Split filter from sort in useMemo.** Changing sort order shouldn't recompute filtering:

```ts
const filtered = useMemo(() => markets.filter(m => m.category === cat), [markets, cat]);
const sorted = useMemo(() => filtered.toSorted(sortFn), [filtered, sortOrder]);
```

**`useDeferredValue` for search/filter over large lists.** Keeps the input responsive while filtering 1000+ markets:

```tsx
const [query, setQuery] = useState("");
const deferredQuery = useDeferredValue(query);
const filtered = useMemo(() => markets.filter(m => fuzzyMatch(m, deferredQuery)), [markets, deferredQuery]);
```

**Passive event listeners for scroll.** Add `{ passive: true }` to touch/wheel listeners on orderbook and explore infinite scroll.

**`requestIdleCallback` for non-critical work.** Schedule analytics, localStorage saves, and prefetching during idle periods:

```ts
function handleOrderPlaced(order: Order) {
  updateUI(order); // Immediate
  requestIdleCallback(() => analytics.track("order_placed", order));
  requestIdleCallback(() => saveToRecentOrders(order));
}
```

**`useEffectEvent` for stable WS callbacks.** Access latest values in WS message handlers without adding them to effect dependency arrays — prevents subscription teardown/setup on every callback change:

```ts
import { useEffectEvent } from "react";
const onMessage = useEffectEvent((msg: WsMessage) => {
  queryClient.setQueryData(key, applyDelta(msg)); // always has latest queryClient
});
useEffect(() => {
  return wsHub.subscribe({ channel: "market", tokenIds }, onMessage);
}, [tokenIds]); // onMessage not in deps — stable
```

**`flatMap` to map and filter in one pass:**

```ts
const validPrices = responses.flatMap(r => r.success ? [r.data.price] : []);
```

### L. View Transitions — Replacing Framer Motion for Navigation

Enable in `next.config.ts`: `experimental: { viewTransition: true }`. Uses React's `<ViewTransition>` component (available via Next.js's internal React canary). Unsupported browsers skip animations gracefully.

**What View Transitions replace (remove Framer Motion for these):**
- Page enter/exit slides → `<ViewTransition enter="slide-from-right" exit="slide-to-left">`
- Shared element morphs (market card → market page) → `<ViewTransition name={`market-${id}`} share="morph">`
- List reorder animations → `<ViewTransition key={item.id}>` per item
- Suspense fallback→content reveals → VT wrapping Suspense boundary
- Fade in/out (AnimatePresence) → `<ViewTransition enter="fade-in" exit="fade-out">`

**What Framer Motion keeps (View Transitions can't do these):**
- Spring physics (orderbook flash animation)
- Gesture-driven animations (drag, swipe)
- Scroll-linked animations
- Complex orchestrated sequences
- Staggered children during page exit

**Key rules:**
- Always use `default="none"` — without it, every VT fires browser cross-fade on every transition (Suspense resolves, revalidations, etc.)
- Always pair `enter` with `exit`
- Place directional VTs in **page components**, not layouts (layouts persist, enter/exit won't fire)
- `router.back()` does NOT trigger view transitions — use `router.push()` with explicit URL
- Named VTs must be globally unique — use IDs (`market-${slug}`)

**Doji-specific animation map:**

| Navigation | Animation | Implementation |
|-----------|-----------|---------------|
| Explore → market page | Directional slide + shared element morph | `<Link transitionTypes={['nav-forward']}>` on card. `<ViewTransition name={`market-${slug}`} share="morph">` on market image in both views. |
| Market → explore (back) | Reverse slide | `<Link transitionTypes={['nav-back']}>` on back button |
| Tab switching (orderbook/positions/activity) | Fade or `default="none"` | Lateral — no depth to communicate |
| Suspense reveals (data loading) | Slide up | `<ViewTransition enter="slide-up" default="none">` wrapping content |
| Explore grid filter/sort | Per-item identity | `<ViewTransition key={market.id}>` per card, trigger in `startTransition` |
| Same-route market switch | Key + share | `<ViewTransition key={slug} name={`market-${slug}`} share="auto" default="none">` |

## 13. Component System

### Three Hard Tiers

Every component belongs to exactly one tier. The tier determines what it can import and what it knows about.

**Tier 1 — Route Modules** (`app/`)
- Always Server Components unless explicitly `"use client"`
- Only responsibility: prefetch data, set up metadata, create Suspense boundaries
- Maximum file size: ~60 lines
- Allowed imports: tRPC server client, domain container components (Tier 2), `<Suspense>`, `<HydrationBoundary>`
- Not allowed: Zustand, `useQuery`, browser APIs

**Tier 2 — Domain Containers** (`domains/`)
- `"use client"` if they own state or handle events
- Own queries (`useQuery`), mutations (`useMutation`), Zustand subscriptions
- Know about the domain they're in; know nothing about other domains' internals
- Compose from Tier 3 components
- File names: descriptive noun, optionally suffixed `-container` for the top-level component

**Tier 3 — Design System** (`ui/`)
- No `"use client"` at module level (event handlers in props are fine)
- Zero imports from `@/domains/`, `@/stores/`, `@/lib/trpc/`, `@/lib/ws/`
- Receive typed props; render HTML
- Testable with `render(<Button />, {})` — no providers needed

### When to use `"use client"`

The decision is mechanical:
- Needs `useState`, `useEffect`, `useRef` → `"use client"`
- Needs `useQuery` or Zustand → `"use client"`
- Needs browser APIs → `"use client"`
- Async function that fetches data → Server Component (no `"use client"`)
- Renders based on server data only → Server Component

### Composition Patterns (from Vercel Engineering)

**Rule: No boolean props for behavioral variants.** Each boolean doubles possible states. 5 booleans = 32 code paths.

```tsx
// ❌ Boolean prop proliferation — 8 code paths, most untested
<OrderForm isBuyMode isLimitOrder showDepth />

// ✅ Explicit variant components composing shared internals
<LimitOrderForm side="BUY">
  <OrderForm.PriceField />
  <OrderForm.AmountField />
  <OrderForm.DepthPreview />
  <OrderForm.Submit />
</LimitOrderForm>
```

**Compound components for complex UI.** Structure as `Component.SubComponent` with shared context:

```tsx
// Orderbook as compound component
<Orderbook.Provider tokenId={tokenId}>
  <Orderbook.Header />
  <Orderbook.AskRows />
  <Orderbook.Spread />
  <Orderbook.BidRows />
</Orderbook.Provider>

// Chart as compound component
<Chart.Provider conditionId={conditionId}>
  <Chart.Toolbar />
  <Chart.Canvas />
  <Chart.TimeframeSelector />
</Chart.Provider>
```

**State context interface — decouple UI from state management:**

Define a generic interface with `state`, `actions`, `meta`. The provider is the only place that knows how state is managed. UI components consume the interface.

```ts
type OrderFormContextValue = {
  state: { price: string; amount: string; side: "BUY" | "SELL"; type: OrderType; isSubmitting: boolean };
  actions: { setPrice: (v: string) => void; setAmount: (v: string) => void; submit: () => void };
  meta: { tickSize: number; minOrderSize: number; balance: number };
};
```

Different providers implement this: `MarketOrderProvider` (no price field), `LimitOrderProvider` (with price), `EditOrderProvider` (pre-filled from existing order). The same `OrderForm.Input` and `OrderForm.Submit` work with all providers.

**React 19 specifics:**
- Use `use(Context)` instead of `useContext(Context)` — can be called conditionally
- Use `ref` as a regular prop — no `forwardRef`

### Component Taxonomy (from building-components skill)

Every UI artifact in the codebase falls into one of these categories. Use this to decide where something lives and how it's structured:

| Level | What it is | Doji example | Lives in |
|-------|-----------|-------------|---------|
| **Primitive** | Unstyled behavior + a11y. No visual design. | Radix Dialog, Base UI Popover | `node_modules` (never custom) |
| **Component** | Styled, reusable UI unit wrapping a primitive | `Button`, `Input`, `Tooltip`, `Badge` | `ui/primitives/` |
| **Pattern** | Documented composition solving a UX problem | Optimistic UI, confirm-before-delete, typeahead search | `ui/patterns/` |
| **Block** | Opinionated product-specific composition | Order form, orderbook panel, bridge deposit flow | `domains/{domain}/components/` |
| **Page** | Single-route view composing blocks | `/market/[slug]`, `/explore`, `/portfolio` | `app/` route modules |
| **Utility** | Non-visual helper (hook, function) | `useDebounce`, `cn()`, `formatPrice()` | `hooks/`, `utils/`, `lib/` |

**Classification heuristic:** If it has no styling → primitive. If it's styled + reusable across domains → component. If it solves a product-specific use case → block. If it's a full route → page.

### `data-slot` for Component Identification

Use `data-slot` attributes on compound component parts for stable parent→child styling. This replaces fragile element selectors and avoids className prop explosion:

```tsx
// Orderbook compound component with data-slot
function OrderbookHeader(props: React.ComponentProps<"div">) {
  return <div data-slot="orderbook-header" {...props} />;
}

function OrderbookRow(props: React.ComponentProps<"div"> & { side: "bid" | "ask" }) {
  return <div data-slot="orderbook-row" data-side={props.side} {...props} />;
}

// Parent can target children without knowing their internals
<div className="[&_[data-slot=orderbook-row][data-side=bid]]:text-positive
               [&_[data-slot=orderbook-row][data-side=ask]]:text-negative">
  <OrderbookHeader />
  <OrderbookRow side="bid" />
  <OrderbookRow side="ask" />
</div>
```

### `data-state` for Visual State Styling

Expose component state via `data-state` attributes instead of multiple className props. Style with Tailwind's `data-[]` variant:

```tsx
// Order form submit button — state exposed as data attribute
<button
  data-slot="submit-button"
  data-state={isSubmitting ? "loading" : isDisabled ? "disabled" : "ready"}
  className="data-[state=loading]:opacity-50 data-[state=disabled]:cursor-not-allowed"
>
  {isSubmitting ? "Placing..." : "Place Order"}
</button>
```

### Controlled + Uncontrolled State

Domain blocks (order form, bridge flow) should support both controlled and uncontrolled usage. Use `useControllableState` from Radix for components that need this:

```ts
import { useControllableState } from "@radix-ui/react-use-controllable-state";

// Order form price field — works controlled (parent manages) or uncontrolled (self-manages)
const [price, setPrice] = useControllableState({
  prop: controlledPrice,       // from parent (if provided)
  defaultProp: defaultPrice,   // initial value (if uncontrolled)
  onChange: onPriceChange,     // notify parent of changes
});
```

### `render` Prop for Element Polymorphism (Base UI)

We use Base UI (not Radix). Base UI uses `render` prop instead of `asChild` for element polymorphism. Same goal — avoid wrapper div nesting — different API:

```tsx
// Base UI render prop — single DOM element, no wrapper
<Tooltip.Trigger render={<Link href={`/market/${slug}`} />}>
  {marketTitle}
</Tooltip.Trigger>

// Dialog trigger using our Button component
<Dialog.Trigger render={<Button variant="outline" />}>
  Place Order
</Dialog.Trigger>

// For custom rendering logic, render accepts a function:
<Dialog.Trigger render={(props) => <MyCustomButton {...props} />}>
  Open
</Dialog.Trigger>
```

**Key Base UI differences from Radix (already migrated, but worth knowing):**
- `render` prop replaces `asChild` — accepts element or render function
- Positioned popups (Select, Tooltip, Popover, Dropdown) require a `Positioner` wrapper component with `side`/`align` props (Radix put these on `Content`)
- Labels in popups must be inside a `Group` component
- `useRender` hook + `mergeProps` for building custom composable components

### Loading State Pattern

Two patterns, applied based on whether the skeleton matches the data shape:

**Pattern A:** `loading.tsx = null` + page owns the `<Suspense>` + skeleton
- Use when: skeleton structure mirrors the content structure (trading layout, explore grid)
- Advantage: you control when/where the skeleton appears, can be more granular

**Pattern B:** `loading.tsx = <PageSkeleton />`
- Use when: a full-page generic skeleton works (portfolio, leaderboard)
- Advantage: zero setup in the page component

## 14. Error Model

One error class. No exceptions (pun intended).

```ts
// packages/server/src/errors.ts

import { TRPCError, type TRPC_ERROR_CODE_KEY } from "@trpc/server";

export class AppError extends TRPCError {
  readonly why?: string;   // what went wrong, human-readable
  readonly fix?: string;   // what the user can do about it
  readonly link?: string;  // a URL for more info or to take action

  constructor(opts: {
    code: TRPC_ERROR_CODE_KEY;
    message: string;
    why?: string;
    fix?: string;
    link?: string;
    cause?: unknown;
  }) {
    super({ code: opts.code, message: opts.message, cause: opts.cause });
    this.why = opts.why;
    this.fix = opts.fix;
    this.link = opts.link;
  }
}
```

The tRPC error formatter uses `instanceof`, not duck-typing:

```ts
errorFormatter({ shape, error }) {
  const appErr = error.cause instanceof AppError ? error.cause : null;
  return {
    ...shape,
    data: {
      ...shape.data,
      zodError: error.cause instanceof ZodError ? flattenError(error.cause) : undefined,
      why:  appErr?.why,
      fix:  appErr?.fix,
      link: appErr?.link,
    },
  };
},
```

Usage in routers:

```ts
// Simple error — no user-facing context needed
throw new AppError({ code: "NOT_FOUND", message: "Market not found" });

// Actionable error — user needs to know what to do
throw new AppError({
  code: "PRECONDITION_FAILED",
  message: "Insufficient balance",
  why: "Your pUSD balance is below the minimum order size of $1",
  fix: "Deposit more USDC to your trading wallet",
  link: "/bridge",
});

// Mapping external API errors
```

### Connection Pattern

Neon exposes two drivers — use the right one for the context:

| Driver | When to use |
|--------|------------|
| `@neondatabase/serverless` (HTTP) | Default for all queries. Fastest for single, non-interactive requests in serverless. |
| `@neondatabase/serverless` (WebSocket) | Required when using transactions (`db.transaction(...)`) — HTTP mode does not support multi-statement interactive sessions. |

```ts
// packages/db/src/client.ts
import { neon, neonConfig, Pool } from "@neondatabase/serverless";
import ws from "ws";

// HTTP client — for regular queries
export const sql = neon(env.DATABASE_URL);
export const db = drizzle(sql);

// WebSocket pool — for transactions only
neonConfig.webSocketConstructor = ws;
export const pool = new Pool({ connectionString: env.DATABASE_URL });
export const dbTx = drizzle(pool);
```

### New Column Convention: Identity over Serial

For all new tables, use `generatedByDefaultAsIdentity()` instead of `serial`. The `serial` type is PostgreSQL-specific legacy shorthand; identity columns follow the SQL standard and give you explicit control over the sequence.

```ts
// ✅ V2 convention
id: integer("id").primaryKey().generatedByDefaultAsIdentity(),

// ❌ Legacy — don't add new serial columns
id: serial("id").primaryKey(),
```

`generatedByDefaultAsIdentity()` allows explicit ID inserts (needed for seed scripts and fixtures); use `generatedAlwaysAsIdentity()` only if you want the DB to strictly own the sequence.

## 16. TypeScript Contracts

### The Pre-Computed Inference Pattern

All procedure input/output types are pre-computed in `@doji/contract`:

```ts
// packages/contract/src/index.ts
export type RouterOutput = inferRouterOutputs<AppRouter>;
export type RouterInput  = inferRouterInputs<AppRouter>;
```

This replaces the current pattern of calling `inferRouterOutputs` at the call site.

### Zod v4

V2 targets Zod v4. tRPC v11+ is compatible. Key changes from v3:

| Change | v3 | v4 |
|--------|----|----|
| String formats | `z.string().email()` | `z.email()` (top-level) |
| Strict object | `.strict()` | `z.strictObject(...)` |
| Error param | `message`, `invalid_type_error` | unified `error` param |
| Error issues | `err.errors` | `err.issues` |
| UUID enforcement | lenient | strict RFC 4122 — test your UUID fixtures |
| Performance | baseline | 14× faster string, 7× faster array, 2.3× smaller bundle |

Import path for tRPC compatibility: `import { z } from "zod"` (root import resolves to v4 after upgrade). The subpath `"zod/v4"` works but some ecosystem tools (trpc-ui) may lag.

Migration: `npx @zod/codemod --transform v3-to-v4 --dry-run ./src` covers most cases automatically.

### Branded Types Are Enforced

Functions that accept domain IDs use branded types. The compiler rejects unbranded strings.

```ts
// ✅ Correct
const book = await getOrderbook(tokenId("0x123..."));

// ❌ Compile error: Argument of type 'string' is not assignable to parameter of type 'TokenId'
const book = await getOrderbook("0x123...");
```

Zod schemas for Gamma/CLOB API responses include branded type coercion at parse time:

```ts
// packages/types/src/polymarket.ts
const marketSchema = z.object({
  conditionId: z.string().transform(conditionId),   // string → ConditionId
  tokenIds:    z.tuple([
    z.string().transform(tokenId),                  // string → TokenId
    z.string().transform(tokenId),
  ]),
  slug: z.string().transform(marketSlug),           // string → MarketSlug
});
```

## 17. Naming Guide

Applied consistently across the entire codebase.

### Files

Always `kebab-case`. Component exports inside files are `PascalCase`.

```
order-form-container.tsx    → export function OrderFormContainer(...)
use-session.ts              → export function useSession()
order-form-store.ts         → export const useOrderFormStore = create(...)
```

### File Suffixes

Suffixes are **required** for files that serve a specific infrastructure role. They are **optional** for general components — a file named `event-card.tsx` is fine on its own. Use `-container.tsx` / `-view.tsx` only when both exist for the same concept (e.g., `orderbook-container.tsx` + `orderbook-view.tsx`).

| Suffix | Required? | Contains |
|--------|-----------|---------|
| `-skeleton.tsx` | Always | Loading state component |
| `-provider.tsx` | Always | React context provider |
| `-modal.tsx` | Always | Dialog or sheet |
| `-store.ts` | Always | Zustand store |
| `-schema.ts` | Always | Zod schema + inferred types |
| `-types.ts` | Always | TypeScript-only type definitions |
| `-constants.ts` | Always | `UPPER_SNAKE_CASE` primitives |
| `-utils.ts` | Always | Pure functions, no side effects |
| `-container.tsx` | Only when `-view.tsx` also exists | Tier 2 component that owns queries or state |
| `-view.tsx` | Only when `-container.tsx` also exists | Tier 3 pure presentational component |
| `-hooks.ts` | When a file has multiple related hooks | Multiple related hooks (for complex feature forms) |

### Directories: `lib/` vs `config/` vs domain constants

| Directory | Contains | Example |
|-----------|---------|---------|
| `lib/` | All logic — pure utilities, transforms, AND external API clients. The `-service.ts` suffix on the file marks external I/O. No separate `services/` directory. | `order-validation.ts`, `clob-read.ts`, `gamma.ts`, `magic-auth.ts` |
| `config/` | Runtime configuration — values that change per environment or are derived from env vars | `query.ts` (staleTime tiers), `app.ts` (isProduction), `features.ts` (flags) |
| Domain `-constants.ts` | Domain-specific fixed values that never change | `explore-constants.ts`, `activity-history-constants.ts` |

### tRPC Procedures

- **Queries:** noun or noun phrase. No `get` prefix.
  - `orders.open` not `orders.getOpenOrders`
  - `markets.orderbook` not `markets.getOrderBook`
  - `portfolio.positions` not `portfolio.getPositions`
- **Mutations:** verb.
  - `orders.place` not `orders.createAndPostOrder`
  - `orders.cancel` not `orders.cancelOrder`
  - `watchlist.toggle` not `watchlist.toggleWatchlistItem`

### Zustand Stores

Store files end in `-store.ts`. The hook export follows `use{Name}Store`:

```ts
// order-form-store.ts
export const useOrderFormStore = create<OrderFormState & OrderFormActions>()(...)
```

Access via selectors (enforced by code review — `useOrderFormStore()` without selector is a lint warning):

```ts
// ✅ Selector — component only re-renders when `side` changes
const side = useOrderFormStore((s) => s.side);

// ❌ Full store — component re-renders on any state change
const store = useOrderFormStore();
```

### Hooks

- **Read hooks:** `use` + noun — `useSession()`, `useOrderbook(tokenId)`, `usePositions(address)`
- **Action hooks:** `use` + verb phrase — `usePlaceOrder()`, `useDeploySafe()`, `useApproveTokens()`
- **Sync hooks** (side effects): `use` + noun + `Sync` — `useMarketSync(tokenId)`, `useAccountSync(address)`
- **No infrastructure names in hooks:** `useOrderClient` not `useClobClient`. `useHeartbeatSync` not `useClobHeartbeat`.

### Zod Schemas

`{entity}{Action}QueryOptions` pattern:

### Event Handlers

- **Internal handlers:** `handle` prefix — `handleSubmit`, `handlePriceChange`, `handleTabSwitch`
- **Prop callbacks:** `on` prefix — `onSubmit`, `onChange`, `onTabChange`

```tsx
// ✅ Internal handler
```

### Boolean Variables

Always prefix with `is`, `has`, `should`, or `can`:

```ts

const isLoading = true;

const shouldRefetch = staleTime < Date.now();
```

PascalCase nouns, exported as namespace:

## 21. Dependency Migrations

### `ethers` v5 → `viem`

**Why:** `ethers` v5 is legacy (v6 has been out 2+ years). `viem` is TypeScript-first, tree-shakeable, and 35x smaller. The Polymarket SDKs already use viem internally — `ethers` is listed as a dep only for backward-compatible type signatures.

**Scope:** 15 files in our codebase import from `ethers` or `@ethersproject/*`. Zero Polymarket SDK blockers.

| Area | Files | ethers usage | viem equivalent |
|------|-------|-------------|----------------|
| Auth/Magic signer | 5 | `Web3Provider`, `JsonRpcSigner` | `createWalletClient({ transport: custom(magicProvider) })` |
| On-chain reads | 3 | `ethers.Contract` for balance, approvals, resolver | `getContract` + `publicClient.readContract()` |
| Bridge/wrap | 3 | `ethers.Contract` for USDC transfer, wrap txs | `getContract` + `walletClient.writeContract()` |
| Trading (CTF) | 4 | `ethers.Contract` for split/merge/redeem, UMA URL | `getContract` + `walletClient.writeContract()` |

**Migration pattern:**

```ts
// Before (ethers v5)
import { ethers } from "ethers";
const contract = new ethers.Contract(address, abi, signer);
const balance = await contract.balanceOf(account);

// After (viem)
import { getContract } from "viem";
const contract = getContract({ address, abi, client: publicClient });
const balance = await contract.read.balanceOf([account]);
```

**Magic SDK signer migration:**

```ts
// Before (ethers)
import { Web3Provider } from "@ethersproject/providers";
const provider = new Web3Provider(magicProvider);
const signer = provider.getSigner();

// After (viem) — simpler, no wrapper needed
import { createWalletClient, custom } from "viem";
import { polygon } from "viem/chains";
const client = createWalletClient({
  chain: polygon,
  transport: custom(magicProvider), // Magic's EIP-1193 provider works directly
});
```

**Packages to remove after migration:**
- `ethers` (1.1MB)
- `@ethersproject/providers` (340KB)
- `@ethersproject/wallet` (270KB)

**Package to add:** `viem` (already a transitive dep via Polymarket SDKs — just add as direct dep).

### `Temporal` API — Replace `date-fns`

**Rule:** Use `Temporal` for all date/time logic. Remove `date-fns` entirely.

`date-fns` is used in ~15-20 files for `formatDistanceToNow`, `format`, `parseISO`, `isAfter`, `addDays`, etc. Every one of these has a native equivalent via `Temporal` + `Intl.DateTimeFormat` — both built into the runtime with zero bundle cost.

**Replacements:**

| `date-fns` | Native replacement |
|-----------|-------------------|
| `parseISO(str)` | `Temporal.Instant.from(str)` or `Temporal.PlainDate.from(str)` |
| `isAfter(a, b)` | `Temporal.Instant.compare(a, b) > 0` |
| `addDays(date, 5)` | `date.add({ days: 5 })` (immutable — returns new object) |
| `differenceInHours(a, b)` | `a.until(b).total({ unit: "hour" })` |
| `format(date, "MMM d, yyyy")` | `new Intl.DateTimeFormat("en-US", { month: "short", day: "numeric", year: "numeric" }).format(date)` |
| `formatDistanceToNow(date)` | Small utility (see below) |

**Relative time utility (replaces `formatDistanceToNow`):**

```ts
// utils/time.ts — replaces date-fns formatDistanceToNow
function formatTimeAgo(instant: Temporal.Instant): string {
  const seconds = Temporal.Now.instant().since(instant).total({ unit: "second" });
  if (seconds < 60) return `${Math.floor(seconds)}s ago`;
  if (seconds < 3600) return `${Math.floor(seconds / 60)}m ago`;
  if (seconds < 86400) return `${Math.floor(seconds / 3600)}h ago`;
  return `${Math.floor(seconds / 86400)}d ago`;
}
```

## Appendix: Decision Log

| Decision | Alternatives Considered | Why This One |
|---------|------------------------|-------------|
| Session in TanStack Query not localStorage | Keep localStorage; use Jotai atoms; use server cookies only (no client state) | Query cache gives automatic stale/revalidate, 401 handling, and DevTools visibility. localStorage gives none of these. |
| WS writes into Query cache | WS writes into Zustand; keep WS data separate from query data; use Recoil for combined model | TanStack Query is already the caching layer for server data. The WS is just a faster update mechanism for the same data. Unifying them means one truth, one DevTools view, one invalidation API. |
| `AppError extends TRPCError` | Keep two patterns; use Result types (Ok/Err); throw plain objects | Extends the existing infrastructure without breaking the tRPC error serialization pipeline. One class to learn, one place to look. |
| Domain folders (`domains/`) | Keep `features/`; use `modules/`; flatten everything | Domain names outlive page names. `features/explore` will need renaming when the page is redesigned. `domains/explore` keeps the name but removes the `features/` indirection. Each domain is cohesive — bridge, referrals, leaderboard, and tracker are standalone rather than crammed into catch-all directories. |
| `packages/contract` for router types | Keep direct `server/routers/index` import; generate types to a file; put in `packages/types` | Contract is the correct mental model — it's the agreement between server and client. Separate package means the boundary is explicit and the web app has zero runtime dependency on server code. |
| `tracker` not `wallets` for tracked wallets router | Keep `wallets`; use `watching`; use `following` | `wallets` is maximally ambiguous in a trading app — everyone has wallets. `tracker` directly names the feature (Wallet Tracker). |
